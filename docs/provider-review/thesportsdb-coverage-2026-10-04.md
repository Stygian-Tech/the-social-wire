# TheSportsDB Coverage Review — 2026-10-04

The [coverage manifest](./thesportsdb-coverage-2026-10-04.json) records reviewed API identities and sample evidence. The [Development configuration](./thesportsdb-development-reviewed-config.json) contains only competitions with a verified current season and upcoming or recent events that pass the actual SportsCore event normalizer. Full-season mappings additionally require every returned event to normalize within the adapter's payload and row limits. Each property value must be JSON encoded when supplied as a Railway environment variable. These files do not activate access or change the hosted environment.

League metadata was verified using the official public API; schedules and tables were subsequently checked with the existing Development Small Business subscription. Credentials were held in memory and are absent from the review artifacts. Schedule evidence retains only public event IDs and dates. The review uses no artwork.

The actual samples exposed timezone-free UTC timestamps that the original normalizer rejected. Verification was repeated after the parser accepted strict UTC timestamps without an offset, explicit offsets, and fractional seconds. Motorsport, tennis, golf, and combat events were checked with no home/away competitors; title and timestamp are sufficient for their schedule presentation. `normalization` and `seasonNormalization` retain exact sample and parsed counts in the manifest.

The provider's [documentation](https://www.thesportsdb.com/documentation) exposes next/previous league schedules and full season schedules. An identity in its catalog does not prove event coverage. `scheduleReview` distinguishes a current sample from an unprobed or empty competition. The `providerCurrentSeason` field is evidence of the provider's metadata, while `verifiedSeason` comes from actual current events; stale metadata is not an activation instruction. Recent event validation uses September 1, 2026 as its lower bound.

Standings use the V1 table endpoint, documented for featured football leagues. Only nonempty tables that match both the requested league and the verified event season enter the standings configuration. Other sports receive schedules and results without an inferred league table. Tournament identities and an empty off-season response remain recorded for later review.

The [Small Business tier](https://www.thesportsdb.com/docs_pricing.php) is $20/month with 120 requests/minute. Review probes are bounded near one request/second. The documented live-score offering covers football, NFL, NBA, MLB, and NHL; this manifest makes no live-score claims, including for those sports. Five-minute event polling is separate from the provider's two-minute offering.

The [terms](https://www.thesportsdb.com/docs_terms_of_use.php), updated September 17, 2026, permit paid API use within its limits and require source attribution. They prohibit website scraping. The provider's subscription does not clear third-party photographs, logos, or other artwork. The serving UI must identify TheSportsDB as the source and retain timestamps and degradation state.

Missing mappings remain news-only. DCI, NCAA swimming, para swimming, and individual tennis majors are not mapped to an unrelated league to manufacture schedule availability. Follow/mute identity and article resolution remain independent of provider availability.

Team short codes reuse the daily V2 `list/teams/{reviewedLeagueID}` reference refresh. The [short-code audit](./thesportsdb-team-shortcodes-2026-10-04.json) probed all 38 already-reviewed competition mappings: 27 returned team lists, totaling 683 rows and 375 explicit, validated `strTeamShort` codes. NFL, NBA, NHL, WNBA, MLB, EPL, and Championship samples supplied a code for every team; Formula 1 supplied only one of 11. No initials or resolver aliases are converted into codes. Missing or unavailable metadata keeps the full participant name.

A code requires a numeric provider team ID and 2–8 ASCII letters/digits after whitespace and case normalization. Conflicting codes are suppressed within a competition, while reviewed canonical codes take precedence. Stable identities and last successful code metadata survive same-ID team renames and provider outages. The `reference:{competitionID}:v3` resource key schedules one bounded refresh of the new attribute without clearing old snapshots or claim history; successful refreshes keep the daily shared-reader cadence. Failed attempts retain the prior snapshot and defer their own fenced claim for five minutes, rather than suppressing retries for a full day. The one-resource-per-cycle budget remains unchanged.
